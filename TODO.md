## 4. Платные курсы и оплата

Курс может быть платным. Сейчас у курса есть только режим записи `enrollment` (`open` или `request`), цены и оплаты нет.

### Что решить до начала

- [ ] Платёжный провайдер. Для России: ЮKassa, CloudPayments, Тинькофф Касса; для остального мира: Stripe. Определяет формат webhook, комиссию и требования к чекам.
- [ ] Модель денег: все платежи идут владельцу платформы, а преподавателям выплаты вручную; или платформа — маркетплейс с комиссией и выплатами преподавателям (это сильно сложнее и требует юридического оформления).
- [ ] Чеки: в России при приёме оплаты нужен онлайн-чек (54-ФЗ), обычно его формирует провайдер или касса. Уточнить у выбранного провайдера и для своего статуса (самозанятый, ИП).
- [ ] Разовая оплата за курс или подписка. Сначала проще разовая.
- [ ] Как цена сочетается с режимами записи (предложение, чтобы не плодить комбинации):
  - свободная запись + цена: «Купить», после оплаты студент на курсе;
  - по заявке + цена: заявку одобряет преподаватель, затем студент платит, и только после этого записывается;
  - приглашение: решает преподаватель — приглашение бесплатное для студента или тоже требует оплаты (флаг «бесплатно по приглашению»).
- [ ] Возвраты: можно ли вернуть деньги и в какой срок (например, до первого завершённого теста), кто решает, что происходит с доступом.
- [ ] Валюта: одна или несколько. Начать с одной.

### Бэкенд

- [ ] Поля курса: `price_minor` (сумма в копейках или центах, целое число, `0` — бесплатный) и `currency`. Деньги не хранить дробным числом. Миграция, схемы, правка курса (`PATCH`), создание курса.
- [ ] Таблица `payment`: `id`, `course_id`, `student_id`, `amount_minor`, `currency`, `status` (`created`, `pending`, `paid`, `failed`, `refunded`, `cancelled`), `provider`, `provider_payment_id`, `idempotency_key`, `created_at`, `paid_at`. На пару «курс и студент» один незавершённый платёж.
- [ ] Цену в платёж брать с сервера в момент создания, а не из запроса клиента. Сумму не принимать от фронта.
- [ ] `POST /course/{id}/pay`: создаёт платёж у провайдера и возвращает ссылку на оплату (редирект на страницу провайдера). Карточные данные через наш сервер не проходят.
- [ ] `POST /payments/webhook`: приём уведомлений провайдера. Обязательно проверять подпись, обрабатывать идемпотентно (повторная доставка не должна записать студента дважды), отвечать быстро.
- [ ] Запись на курс после подтверждения оплаты делает только webhook (или проверка статуса у провайдера), а не возврат пользователя на сайт: пользователь может закрыть вкладку.
- [ ] `/course/{id}/enroll` и принятие приглашения для платного курса отклонять, пока нет оплаты.
- [ ] Возвраты: `POST /payments/{id}/refund` для преподавателя или администратора, статус `refunded`, что делать с доступом по решению из раздела «Что решить».
- [ ] Не терять платёж: задача планировщика сверяет зависшие `pending` платежи со статусом у провайдера.
- [ ] Каталог (`/course/catalog`) и список курсов отдают цену и признак «куплено».
- [ ] Удаление курса и аккаунта с оплаченными платежами: платежи не удалять (учёт), нужна политика. Преподавателю нельзя удалить курс с оплатами без явного решения. Сейчас `delete_account` и `delete_course` об оплатах ничего не знают.
- [ ] Секреты провайдера (ключи, ключ подписи webhook) только из окружения. Тестовый режим провайдера для разработки.
- [ ] Тесты: покупка, повторный webhook, неверная подпись, подмена суммы клиентом, оплата уже записанным студентом, платёж отменён, возврат. Провайдера подменять заглушкой.

### Фронтенд

- [ ] Преподаватель: поле «Цена» в создании и редактировании курса (с переключателем «бесплатный»), хранить в минимальных единицах.

- [ ] Студент: статусы «ждёт оплаты» после одобрения заявки, понятное сообщение при отказе провайдера.
- [ ] Страница или блок «Мои платежи» в профиле: что, когда, сколько, статус, чек.
- [ ] Преподаватель: доход по курсу, список оплат (можно вместе с аналитикой).

- [ ] Страницы с условиями: оферта, политика возврата, политика конфиденциальности. Для приёма платежей обычно обязательны.
